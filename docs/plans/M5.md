## What an issue contains (§11, §6a)

In this order:

1. **Masthead:** the site name in the town's colors, and the date in the town's timezone.
2. **`newsletter.top`:** the presenting sponsor, labeled "Sponsored". If none is sold, nothing renders (see D-M5-4).
3. **Weather:** today's and tonight's periods from the latest NWS zone forecast. Any active alert comes first, in a box, with its link.
4. **Top stories:** 5 to 8 items picked by `rankArticles()` from stories published since the last issue (on the first day, the last 24 hours):
   - at least one civic item when one exists;
   - public safety capped at 20% (one item in a 5–8 item issue);
   - Tier 3 stories only once a person has approved them, which is already true of anything published.
   - Each item shows its headline, dek and a link to the story, so the sources are one click away (Rule 4).
5. **`newsletter.mid`:** a sponsor or a house ad.
6. **Coming up:** public meetings in the next 7 days, from the calendar source, with links.
7. **Corrections:** any corrections published since the last issue (§6a honesty; this is cheap to add).
8. **Footer:**
   - "Written by the {Site Name} Newsroom (AI-assisted) from public records. How we report →" (Rule 2 and the Methods page).
   - Mail-5's unsubscribe link and postal address.

**The rest of the email:**
- **Subject:** `{Weekday}: {lead headline}`. Plain and factual; no questions and no superlatives (§6a headline rules).
- **Preheader:** the next two headlines.
- **Plain-text part:** carries the same content.

**Design:** email-safe HTML: tables, inline styles, system fonts, and the town's theme colors, checked against the contrast rules. No images in v1, and no open-tracking pixels or tracked links (D-MAIL-12).

## How it runs

- **Every 5 minutes**, the worker checks each town whose mail domain sends bulk mail and whose newsletter isn't `off`.
- **Building the issue:**
  - Once the town's local time passes its send time and no issue exists for that local date, the worker builds one.
  - It stores it in `newsletter_issues`, which is unique per town and date, so a retry never builds a second issue.
  - It then hands the issue to Mail-5 as an `email_campaign` of kind `newsletter`.
- **Who receives it:** in `test` mode, only the town's test list; in `live` mode, every active subscriber.
- **Throttling:** Mail-5's sender throttles and caps the send as it already does.
- **Late builds:** if building fails, it retries on the next tick. More than 3 hours late, it skips that day and logs why.
- **Stats:** each issue's `stats` holds counts copied from Mail-5's per-send statuses: sent, delivered, bounced and complained. No opens are counted.

## Admin

- **Admin → Newsletter:** one row per town showing its mode, send time, last issue and subscriber count.
- **A town's page:**
  - a preview of what tomorrow's issue would contain, from current data;
  - past issues with their stats;
  - "Send a test to me";
  - the mode switch: `off → test → live`.
  - "live" is the standing approval from D-MAIL-11. It is admin-only and audited.

## Decisions for the owner

**D-M5-1 — Thin days.** Some small towns won't have 5 new items every day.
→ **Recommend:**
- Send when there are at least 3 new items, or an active weather alert.
- Otherwise skip the day and log it. A weather-only email isn't worth a send and trains readers to ignore us.
- If there are 3 or 4 items, send them; never pad with old stories.

**D-M5-2 — "Test list first."**
→ **Recommend:**
- Each town has a test list: staff addresses chosen on the town's page.
- New towns start in `test`. Issues go daily to the test list only.
- An admin switches the town to `live` after at least 3 test issues have gone out; the code enforces the 3.
- An admin can drop a town back to `test` or `off` at any time.

**D-M5-3 — "Events" with no events source yet.**
→ **Recommend:**
- Use the upcoming public meetings from the city calendar we already ingest, titled "Coming up".
- Community events come with a real events adapter later.
- Never list events scraped from other outlets (Rule 3).

**D-M5-4 — Sponsor slots.** §11 says "one labeled sponsor slot"; §11b lists `newsletter.top`, `newsletter.mid` and `newsletter.classifieds`.
→ **Recommend:**
- At most one paid unit per issue: the top slot if sold, otherwise the mid slot.
- The mid slot falls back to a house ad ("Advertise in {Site Name}", or "Forward this to a neighbor" with the signup link).
- An unsold top slot renders nothing, so readers don't get two house ads.
- Classifieds wait for the directory (M6).
- The fill order and labels are the same as on the site.

**D-M5-5 — Clicks.**
→ **Recommend:** add `?ref=newsletter` to story links, so the existing cookieless counters (D-M4-3) can count newsletter clicks per story. No per-reader tracking.

**D-M5-6 — Archive of past issues on the site.**
→ **Recommend:** not in M5. Each story is already on the site, and an archive page would duplicate them. Revisit with the M4b redesign.

**D-M5-7 — Send time.** Each town's config already has `newsletter_send_time` (Boca: 06:30).
→ **Recommend:** keep it per town, in local time. Issues go out within about 10 minutes of it, depending on list size and the warm-up cap.
