## M0: Scaffold

### Repo layout

This follows CLAUDE.md §4. M0 and M1 only fill in what they need. The other packages get a `package.json`, an `index.ts` and a README line so the workspace graph is in place from the start.

```
apps/
  web/                 # M1
  worker/              # M0
packages/
  db/                  # M0: schema, migrations, client, queries
  config/              # M0: town YAML zod schema + loader, brand tokens, model config placeholder
  adapters/ pipeline/ prompts/ launcher/ email/ directory/   # stubs only
towns/fl/boca-raton.yaml
docs/plans/M0.md
.github/workflows/ci.yml
docker-compose.yml     # local Postgres 16
.env.example
CLAUDE.md
```

### Tooling

- **pnpm workspaces** with `packageManager: pnpm@10.x` pinned. Node 22 LTS pinned in `.nvmrc` and `engines`.
- **Turborepo** to run `lint`, `typecheck`, `test` and `build` across packages with caching. It's free and local only; remote caching stays off.
- **TypeScript 6.0.x** strict mode with a shared `tsconfig.base.json`. Internal packages are consumed as TypeScript source (`"exports": "./src/index.ts"`), so there's no package build step. Next transpiles them with `transpilePackages`, and the worker runs through `tsx` in dev and is bundled with `tsup` for prod.
- **ESLint 10** flat config with typescript-eslint, plus **Prettier**. One custom lint rule: no `process.env` outside `packages/config/src/env.ts`. All environment variables are read and validated (zod) there, so a missing secret fails at boot, not in the middle of a job. This backs rule 11.
- **Vitest 5** at the root, using a workspace setup per package.

### Database (`packages/db`)

- Drizzle ORM with the `postgres` (postgres.js) driver.
- **Migrations:** `drizzle-kit generate` writes SQL into `packages/db/migrations/`, and that SQL is committed. A small `migrate.ts` script applies it (`pnpm db:migrate`). CI fails if the schema and the migrations are out of sync (`drizzle-kit check`, plus regenerating and checking for a non-empty diff).
- **Local dev:** `docker compose up db` starts Postgres 16. `pnpm db:reset` drops, migrates and seeds.
- **The schema covers all of §5 in the first migration**, not just what M1 needs. Later milestones then add columns without rewriting the core tables. Specifics:
  - **IDs:** `uuid` primary keys (`gen_random_uuid()`).
  - **Timestamps:** `created_at` / `updated_at` (`timestamptz`) on every table.
  - **Enums as Postgres enums:** town status and tier, source kind and health, article status, placement product and status, lead kind, staff role, subscriber status.
  - **`towns`:** `slug` and `domain` are unique. I'll add `extra_domains text[]` for `www.` and dev aliases, plus `network_badge` (always true, no override).
  - **`records`:** `unique(source_id, external_id)` and an index on `(town_id, occurred_at)`.
  - **`articles`:** `unique(town_id, slug)`, and an index on `(town_id, status, published_at desc)` for the home page.
  - **Article checks in the database:**
    - `check (status <> 'published' or byline like '% Newsroom (AI-assisted)%')`. This backs rule 2 at the database level, not only in the app.
    - `check (status <> 'published' or cardinality(source_record_ids) > 0)`. This backs rule 4: an article can't be published without sources.
  - **Arrays for now:** `source_record_ids` and `record_ids` stay `uuid[]` as in §5. A join table (`article_sources`) would give real foreign keys, but it's more than M0 needs. See Decision D7.
  - **`corrections`:** foreign key to `articles` with `on delete restrict`. Corrections can never vanish.
  - **`placements`:** a partial unique/check approach for "max 3 sponsored slots per category per town" is deferred to M6. In M0 it's just the table.
  - **`ai_usage`:** `numeric(10,4)` for `est_cost_usd`.
- **`packages/db` exports:**
  - `db` (the client)
  - the schema
  - typed queries M1 needs: `getTownByHost`, `listPublishedArticles`, `getArticle`, `listCorrections`
- **Seeds:**
  - `pnpm towns:sync` reads `towns/**/*.yaml`, validates it with zod, and upserts into `towns`. The YAML is the source of truth for config. The database owns `status` and `readiness_score`, and sync never touches those two.
  - `pnpm db:seed:dev` adds the test article (see M1).

### Town config (`packages/config`)

- A zod schema for the YAML exactly as in §10. Fields marked `TBD` are allowed only while `status` is `draft`.
- `towns/fl/boca-raton.yaml` is created from the §10 example. Source URLs stay `TBD` until M2. I won't invent them.
- `brand.ts` holds the network brand tokens as a single source. Towns may override only `site_name` and a logo path. The schema rejects anything else, so color overrides are impossible.
- `models.ts` is a placeholder holding the §8 model IDs. M3 verifies them against the Anthropic docs before anything calls them.

### Worker (`apps/worker`)

- Boots pg-boss against `DATABASE_URL`. pg-boss creates and migrates its own `pgboss` schema.
- Registers:
  - a `system.heartbeat` cron job that runs every minute, writes a log line and updates `worker_heartbeats` (a one-row table, or I'll fold this into a `system_status` table)
  - empty queue names for `ingest`, `story-finder`, `writer`, `fact-check` and `newsletter`, so M2 and later only add handlers
- Graceful shutdown on SIGTERM and SIGINT (`boss.stop({ graceful: true })`). Structured JSON logs (pino).
- **Done when:** `pnpm --filter worker dev` connects, the heartbeat fires, and an integration test (real Postgres) starts the worker, waits for one heartbeat and stops it cleanly.
- **Note:** pg-boss needs session-level Postgres connections. It can't use a transaction-mode pooler such as PgBouncer in transaction mode or Supabase's port 6543. This affects the database host choice (D3).

### CI (`.github/workflows/ci.yml`)

- Runs on every PR and on pushes to `main`. Ubuntu, Node 22, pnpm cache, and a `postgres:16` service container.
- Steps, in order:
  1. `pnpm install --frozen-lockfile`
  2. lint
  3. typecheck
  4. migration drift check
  5. `db:migrate` against the service database
  6. unit and integration tests
  7. `next build`
  8. Playwright end-to-end tests (from M1)
- No secrets are needed. Everything runs against the local service database.
- The prompt eval gate (§12) is out of scope until M3/M8. The workflow has a placeholder job name for it.

### `.env.example`

- **Every variable from §14**, empty, with a one-line comment each.
- **Used in M0/M1:** `DATABASE_URL`, `APP_BASE_URL`, `ADMIN_EMAILS` (validated but unused until M3).
- **One new variable (I'll add it to CLAUDE.md §14 too):** `DEV_TOWN_SLUG`, an optional dev-only override for host resolution.
- The company name (`TownCore`) and public contact email (`info@towncore.net`) aren't secrets, so they live as constants in `packages/config/src/network.ts`, not in env vars.

### M0 done when

- `pnpm i && docker compose up -d db && pnpm db:migrate && pnpm test` passes on a clean clone
- The worker boots and the heartbeat runs
- CI is green on the PR
- `.env.example` matches `env.ts` (a unit test checks this)

## M1: Multi-tenant site (`apps/web`)

> **Superseded 2026-10-15 by `docs/plans/M1.md`** after UPDATE-01 (design system, layouts, slot contract). Kept for history.

### Host → town resolution

- A Next.js `middleware.ts` reads the `Host` header and strips the port and `www.`, then looks up the town by `domain` or `extra_domains`.
  - The lookup uses a small cached query: in-memory with a 60-second TTL.
  - The middleware rewrites internally to `/_t/[townSlug]/...`, so every page is a normal App Router route with a `townSlug` param. The URL the visitor sees stays clean (`bocatownsquare.com/about`).
- **Dev and preview:** `boca-raton.localhost:3000` resolves by slug, so no hosts-file edits are needed. Vercel preview URLs use `DEV_TOWN_SLUG`.
- **Unknown host:** a plain 404 page that mentions the TownCore Local network. Unknown hosts never fall back to a default town.
- **No network host.** `towncore.net` is internal and is not served by this app (D2). The network About page lives on every town site at `/network`.

### Indexing safety

A town with `status` `draft` or `paused` gets `X-Robots-Tag: noindex, nofollow` and a `noindex` robots meta tag. A test checks this.

This means pointing BocaTownSquare.com at the app before launch can't get thin or test content indexed (rule 7). It only flips when someone sets the town `live` in the database.

### Brand and layout

- **Colors:** CSS custom properties from `packages/config/brand.ts` (`--navy`, `--brick`, `--teal`, `--paper`, `--slate`) in `globals.css`.
  - Body background is paper, body text is slate, headlines are navy, buttons are brick with white text, and the header/footer bar is navy with paper text.
  - Plain CSS modules, no Tailwind, to keep the dependency count low (D10).
- **Fonts:** self-hosted via `next/font/google`, so there's no runtime request to Google. Inter for the UI, Source Serif 4 for headlines (D5).
- **Header:** site name as a text wordmark in the serif. The logo slot reads from town config (`logo` path), so your logos drop in later without code changes (D12), nav: Home · About · Methods · Corrections.
- **Footer** (rendered by the root layout, so no page can skip it):
  - **"Part of the TownCore Local network"** badge linking to the site's own `/network` page (company name + contact email), which satisfies rule 1 without making towncore.net public
  - links to About, Methods and Corrections
  - © year, site name
- Mobile first, no client JavaScript on content pages (server components only), system-font fallback while web fonts load.

### Pages (all server-rendered, per town)

| Route | Content |
| --- | --- |
| `/` | Site name, a short tagline, the latest published articles for the town (an empty state if there are none) |
| `/about` | Who we are. Covers: <ul><li>AI-assisted local newsroom</li><li>part of TownCore Local, operated by **TownCore** (D1)</li><li>contact email (`info@towncore.net`)</li><li>what we cover</li><li>what we don't do (no rewriting other outlets, no mugshots, etc.)</li><li>how to report an error</li></ul> |
| `/methods` | How stories are made. Covers: <ul><li>primary public sources only</li><li>the pipeline in plain words</li><li>a separate AI fact-check</li><li>risk tiers and which stories always get a human</li><li>byline meaning</li><li>sponsored labeling</li><li>corrections policy</li></ul> |
| `/corrections` | Corrections policy, and a list of every correction for this town (date, article link, note). Empty state: "No corrections yet." |
| `/network` | Network About: company name, contact email, list of live sites (only `status = live` towns) |
| `/news/[slug]` | Article page: <ul><li>headline, dek</li><li>byline from `buildByline()` (§2.2), published/updated dates in the town's timezone</li><li>body (Markdown rendered and sanitized)</li><li>**Sources** list linking to each source record</li><li>corrections shown on the article</li><li>a "Report an error" link</li></ul> |

- **About, Methods and Corrections copy** lives as Markdown templates in `apps/web/content/` with `{site_name}`, `{town_name}` and `{company}` placeholders. One copy serves every town, so the copy can't drift between sites. I'll draft it; **you review the wording** before it goes to production.
- **Bylines:** `buildByline(siteName, reviewerName?)` in `packages/pipeline` is the only way a byline string is made. It has unit tests, and the database check constraint backs it up.
- **Report an error (M1):** a `mailto:` link to the corrections email, prefilled with the article URL. The real form, with a database table and spam protection, comes in M4 (D6).

### Test article

M1's done-when asks for "a test article". My proposal:

- A dev seed (`pnpm db:seed:dev`) inserts one Boca article.
  - Its headline is prefixed **"[TEST]"**, its body explains it's a test, and it has one test source record pointing at the City of Boca Raton homepage.
  - It has one test correction, so the corrections UI is exercised.
- It is inserted **only** when `NODE_ENV !== 'production'` or with an explicit `--allow-test-content` flag, and it is always `noindex`.
- It never goes onto the production database as published news.

  - host normalization
  - town YAML schema (valid Boca config, and rejecting color overrides)
  - `buildByline`
  - brand contrast pairs
  - env schema matches `.env.example`
- **Integration (real Postgres):**

- **End to end (Playwright against `next start`, with the Host header set):**

### Deployment in M1

Rule 10 says no production deploy without human approval. So M1 is done in two steps:

1. **Verified without production.** Everything above passes in CI and on a **Vercel preview** deployment (if you give access). This is where I'd mark M1 done.
2. **Production domain (your approval).** Once you approve:
   - attach `bocatownsquare.com` + `www` to the Vercel project
   - DNS is already on Vercel (D8), so there's no Cloudflare step
   - run `db:migrate` + `towns:sync` against the production database

   The town stays `draft`, so it's `noindex`. It's a real URL showing the site, but nothing gets indexed until launch.

I'll write the deploy steps as a checklist in `docs/deploy.md` rather than automate them in M1. The launcher (M7) automates them later behind `--dry-run`.
