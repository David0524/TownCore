## Design

### 1. The model layer: `packages/pipeline/src/llm.ts` (§8)

- **One function.**
  - Input: `{ job, townId, tier: 'routine' | 'writer' | 'factCheck', system, input, schema, effort }`.
  - Output: a value that has passed the zod schema.
  - It is the only place that imports `@anthropic-ai/sdk`, so the pipeline stays model-agnostic.
- **Models and prices** live in `packages/config/src/models.ts`, together with the date they were verified.
- **Every call writes an `ai_usage` row**: tokens in, tokens out, cache tokens, estimated cost, job, model and prompt version. Refused and failed calls are logged too.
- **Daily spend cap per town.**
  - Set in town YAML as `ai_daily_cap_usd`. Default: $5.
  - It's checked before every call. Once a town hits it, its pipeline jobs pause until midnight in the town's timezone, and the `ai_usage` log shows a warning.
  - The "cost per article up more than 50% week over week" alert comes in M8 with the dashboards.
- **Prompt caching.** Each job's system prompt (rules, style guide, output schema) is fixed text, so repeat calls pay mostly cache-read prices.
- **Tests never call the API.**
  - Recorded responses replay from `packages/pipeline/fixtures/llm/*.json`, the same idea as the adapter fixtures.
  - `pnpm llm:record` refreshes them, using the API key.

### 2. Prompts: `packages/prompts`

- Versioned files: `writer.v1.md`, `factcheck.v1.md`, `classify.v1.md`, `update.v1.md`.
- Each article stores the prompt versions that produced it.
- Prompts carry the style rules from §6:
  - plain, factual, local-newspaper tone
  - no speculation
  - no adjectives about people
  - quotes only when they appear verbatim in a source
  - headlines: no questions, no clickbait, no unsupported superlatives

### 3. Story finder (§6 step 2, §6a)

**Schedule.** `story-finder.tick` runs every 30 minutes and enqueues one `story-finder` job per town that has new or changed records.

**Grouping is done in code, per source type:**

| Records | Becomes |
| --- | --- |
| One News Flash release | One candidate (with records that share its subject linked in) |
| One meeting on the calendar | Not a story by itself. It feeds a weekly "Meetings this week" roundup and, later, previews (D-M3-6). |
| Sunbiz filings from one week | One "New businesses registered in Boca this week" roundup |
| DBPR licenses first issued that week | One "New contractor licenses" roundup |
| NWS alert | A **templated** Tier 1 item written by code from the alert text, with no writer call. The daily forecast stays a homepage module, not an article. |
| A changed record that a published article cites | A follow-up candidate (section 7) |

**Classification** is one Haiku call per candidate. It returns:
- beat
- whether the story is about *this* town (wrong-town check, first pass)
- people named, and the role of each: official, business owner, private person, minor
- impact, novelty and proximity, each scored 0–1, with a one-line reason

**Newsworthiness score** (`packages/pipeline/src/scoring.ts`, 0–100):
- **Timeliness** is computed in code from dates.
- **Reader interest prior:** a fixed per-beat default until M4 collects click data.
- **Penalties:**
  - similar to a story from the last 14 days
  - thin source material (under about 400 characters of real text)
  - a source in `degraded` health
- The weights are constants in that file. Every candidate stores its components in `article_scores` so the weights can be tuned later from data.

**Daily story budget** (in config by town size, overridable in YAML):

| Town size | Items per day |
| --- | --- |
| small | 3 |
| mid | 6 |
| large (Boca) | 10 |

- Public safety is capped at 20%.
- Candidates are written in score order, above the town's threshold (default 40), until the budget is used up.
- Low scorers that belong together become roundups.
- Everything else goes to `skipped_candidates` with a reason:
  - `below_threshold`
  - `budget_full`
  - `duplicate`
  - `wrong_town`
  - `tier4`
  - `thin_source`
  - `public_safety_cap`

### 4. Writer (§6 step 3)

- **Sonnet 5.5, effort `medium`.**
- **Input:** the candidate's record texts, labeled by record ID; the town's name, agencies and timezone; and the beat.
- **Never given:** other news outlets' articles. A record from an `other_outlet` source can't be the basis of a full article; the code blocks that, not the prompt.
- **Output schema:** `{ headline, dek, body_md, beat, source_record_ids, claims[] }`.
  - `source_record_ids` must be a subset of the candidate's records. Code checks this.
  - The slug comes from the headline, made unique per town.
  - The byline comes from `buildByline`.

### 5. Fact-check (§7)

- **A separate Sonnet call, effort `high`.** It never sees the writer's prompt or reasoning, only the draft and the cited records.
- **The model returns, for each claim:** `{ claim, record_id, quote, supported }`, plus a wrong-town judgment.
- **Code then checks the model's work deterministically:**
  - Every `quote` must appear **verbatim** in the cited record's text, after normalizing whitespace and quote marks only. Otherwise the claim is unsupported, whatever the model said.
  - Every name, number, date, dollar amount and address in the article body must appear character-for-character in a cited record. These are found by pattern matching plus the claim list.
  - Wrong-town check: city names, ZIP codes and agencies in the article are compared against the town's config. Another city's name or ZIP flags `wrong_town_risk`.
- **Result:** `{ score, unsupported_claims[], wrong_town_risk, decision }`.
  - **pass:** score ≥ 0.95, zero unsupported claims and no wrong-town risk. The thresholds are in config.
  - **revise:** the writer gets one retry with the unsupported claims listed for removal.
  - **review:** anything still failing goes to the review queue.

### 6. Tier router (§7)

- **Deterministic rules run first, in code.** The strictest result wins.
  - Beat `public-safety` (police, fire) → at least Tier 3.
  - A named private individual (not a public official, and not a business owner in a business context) → at least Tier 3.
  - Health or inspection failure → at least Tier 3.
  - Signs of a minor → **Tier 4**. Signs include: an age under 18 by regex or classifier; words like "juvenile", "student" or "teen" next to a name; a school-sports individual. A reviewer can override this.
  - An arrest without an official release, a mugshot, a sexual-assault victim, a rumor, or a private person's social post → **Tier 4**.
  - Any `other_outlet`-only basis → can't be an article.
- **Then the model's tier, from classification.** The final tier is the strictest of the two.
- **Routing:**

  | Tier | What happens |
  | --- | --- |
  | 1 | Published when fact-check passes |
  | 2 | Published when fact-check passes, except a random 10% that go to review **before** publishing (D-M3-5) |
  | 3 | Always goes to review |
  | 4 | Status `blocked`, reason logged, never shown. The DB constraint already enforces this. |

- **Rule tests** cover each override, including "Tier 4 never publishes even when fact-check passes".

### 7. Follow-ups (§6a)

**When a follow-up is triggered:**
- A record cited by a published article changes (`records.changed_at`).
- A new record matches a published story on the same source item: the same release ID, the same meeting, the same license or filing number.

**What happens:**
1. The writer drafts a short **dated update note** from the new record only, using `update.v1`.
2. The note is fact-checked the same way as a new story.
3. The note goes through the tier router. The final tier is the stricter of the original article's tier and the update's tier.
4. If it passes, the note is appended to the original story as "**Update, Oct 16, 2026:** …", and the new record is added to the story's sources.

**When a new story is linked instead.** If the follow-up deserves its own story (for example, a project that was proposed is now approved), the new story is linked to the original in both directions.

**Dropped charges.** Any record about dropped charges always produces an update. The story finder can never skip it. (Boca has no police or court source yet, but the rule is in code.)

### 8. Admin and review (`/admin`)

**Where it lives.**
- Admin is served on the internal host only: `APP_BASE_URL`, for example `admin.towncore.net` or localhost in development.
- The proxy never serves `/admin` on a town domain, and a test checks that.
- Admin pages use the TownCore network styling and are `noindex`.

**Staff sign-in (magic link).**
- Staff rows are seeded from `ADMIN_EMAILS`.
- A login token:
  - is random, with only a SHA-256 hash stored
  - expires in 15 minutes
  - can be used once
  - is rate-limited to 5 requests per hour per email
- Sessions are an httpOnly, Secure, SameSite=Lax cookie with a 30-day expiry, stored hashed in `staff_sessions`.
- Email goes through `packages/email` with a provider interface (D-M3-2). In development and CI, the link is printed to the log and nothing is sent.

**Pages.**
- **Review queue** (`/admin/review`): pending items by town, oldest first. Each shows:
  - the tier
  - why it's here (Tier 3, sampled, failed fact-check, or classifier flag)
  - fact-check score
- **Review item:**
  - The draft and its cited records side by side.
  - Each claim highlighted green (supported) or red (unsupported), with the supporting quote.
  - Actions:
    - **Approve:** publish with `Reviewed by {name}`.
    - **Edit:** headline, dek and body in a Markdown editor. Saving re-runs the deterministic checks and shows the result. The reviewer can approve after reading it.
    - **Reject:** requires a reason.
    - **Override Tier 4 minor flag:** admin role only, logged.
- **Skip log** (`/admin/skipped`): skipped candidates with reasons, and a "write it anyway" button that queues the writer.
- **Every action** is written to an `admin_actions` audit table: who, what, when, and a before/after summary.

### 9. Jobs (`apps/worker`)

The queues already exist from M0.

| Queue | When it runs | What it does |
| --- | --- | --- |
| `story-finder` | Every 30 minutes per town (via `story-finder.tick`) | Groups records, scores and budgets, writes the skip log, enqueues `writer` |
| `writer` | Per candidate | Draft, then enqueues `fact-check` |
| `fact-check` | Per draft | Check, possibly one revise, then tier router, then publish or review |

Shared rules:
- Singleton keys stop the same candidate from being processed twice.
- A spend-cap pause or a failed API call retries with backoff.
- A refusal goes to review.

### 10. Data model changes

- **New tables:**
  - `article_scores`: article or candidate ID, newsworthiness, components (JSON), computed_at
  - `skipped_candidates`: candidate_id, reason, detail, created_at
  - `article_updates`: article_id, note_md, record_ids, factcheck, created_at
  - `article_links`: from, to, kind (`follow_up`)
  - `staff_login_tokens`, `staff_sessions`
  - `admin_actions`
- **New columns:**
  - `story_candidates`: `kind` (`story`, `roundup`, `update`, `template`), `key` (unique per town, for dedupe), `article_id`
  - `articles`: `candidate_id`, `prompt_versions`, `review_reason`, `rejection_reason`
  - `ai_usage`: `cache_read_tokens`, `prompt_version`
- **Left for M4:** `entities`, `article_entities` and `pins`, which go with entity pages and ranking.

### 11. Evals (§12)

- **Harness.** `packages/prompts/evals/` holds the cases. Each case is input records plus an expected outcome: the facts that must appear, and the tier.
- **Offline checks run in CI on every PR**, against recorded outputs:
  - schema validity
  - quote-verbatim rate
  - tier correctness
  - no Tier 4 published
- **Live eval.** `pnpm evals --live` re-runs the cases against the API. It's for prompt changes and is run by hand (D-M3-4).
- **Seed cases.** I'll write 20 from real Boca records, including tricky ones:
  - a minor named
  - a wrong-town ZIP
  - an invented number
  - an arrest without a release
- **The 50 hand-graded stories from §12** need a human grader once real drafts exist.
