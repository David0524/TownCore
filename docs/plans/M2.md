## Design

### 1. Adapter framework (`packages/adapters`)

- **The interface:** the `SourceAdapter` contract from §9: `platform`, `kinds`, `detect(url, html)`, `fetch(source, since)` and `healthCheck(source)`. It returns `RawRecord[]`:
  - `externalId`, `type`, `title`, `text`, `url`, `occurredAt`, `raw`
- **Registry:** one folder per **platform**, never per town. `findAdapter(url, html)` runs every adapter's `detect()` and picks the highest confidence. The launcher uses it in M7.
- **Polite fetcher (Rule 8, enforced in code):** every adapter must use it; a lint rule bans bare `fetch` in adapters.
  - `User-Agent` set from config.
  - A **robots.txt check** before every fetch, using the `robots-parser` package with a cached robots file.
  - **At most 1 request per second per host.** In-process for now; it moves to a Postgres-backed limiter if we run several workers.
  - A **hard blocklist**: Google Maps, Yelp, Facebook, Nextdoor and paid sports databases. These throw, and a test proves it.
  - Conditional GET (ETag / Last-Modified), timeouts, and 3 retries with backoff on 5xx.
- **Recorded fixtures:**
  - `pnpm fixtures:record <adapter>` runs the adapter live and saves each HTTP exchange to `packages/adapters/<platform>/fixtures/*.json`.
  - Tests replay those fixtures through the same fetcher with undici's `MockAgent`, so tests and CI never touch the network.
  - Every adapter ships fixtures plus tests (§9).
- **Documents:** PDF agendas and minutes get plain text extracted with `unpdf`. Hard PDFs (scanned or complex) are flagged so M3 can send them to Claude (§3).

### 2. Adapters for M2

| Adapter | Kinds | What it fetches | Reused by |
| --- | --- | --- | --- |
| `nws` | weather | `api.weather.gov` zone forecast plus active alerts for the town's zone (Boca: FLZ168). A `User-Agent` header is required by the API. | Every US town |
| `civicplus` | agenda, events, police, fire, other city news | The platform's RSS/listing endpoints: News Flash (media releases), Calendar (meetings and events) and Agenda Center (if Boca uses it), plus linked PDF agendas and minutes. `detect()` looks for CivicPlus/CivicEngage markers. | **Every CivicPlus city**: a large share of US municipalities, so this is high leverage for the launcher |
| `youtube-channel` | meeting_video | The channel's public RSS feed (`youtube.com/feeds/videos.xml?channel_id=…`), so **no API key** is needed. Records hold the video title, date and URL. Transcripts are an M3 question (D-M2-4). | Any town that posts meetings on YouTube |
| `fl-dbpr` *(recommended, D-M2-2)* | business_filings (licenses) | Weekly DBPR licensee CSVs, filtered to the town by address city/ZIP | All Florida towns; seeds the M6 directory and `license_verified` |
| `fl-sunbiz` *(optional, D-M2-2)* | business_filings (new entities) | Daily new-filing files over public SFTP, filtered by principal address | All Florida towns; powers "new businesses" stories |

**If Boca's agendas aren't on a CivicPlus module** (for example a separate Granicus or Legistar portal), the Boca agenda source becomes that platform's adapter instead. Its first live check (step 1 of the work order) decides this, and I won't guess.

### 3. Sources from config

- **YAML:** `towns/fl/boca-raton.yaml` gets real `platform` and `url` values for each source once they're verified (the `TBD` fields today).
- **Sync:** `towns:sync` also upserts `sources` rows, using the town plus kind plus URL as the key, so YAML stays the source of truth.

### 4. Scheduling and ingest (`apps/worker`)

- **One scheduler job**, `ingest.tick`, runs every 5 minutes. It enqueues an `ingest` job for each source that is due, based on its schedule and `last_run_at`.
  - This scales to thousands of towns. One pg-boss cron per source wouldn't.
  - Jobs use singleton keys, so a source never runs twice at once.
- **The `ingest` job:**
  1. Calls `adapter.fetch(source, since)`.
  2. Upserts into `records`: the unique key is `(source_id, external_id)`; a changed `content_hash` updates the row and marks it changed (feeds M3 follow-ups).
  3. Stores `last_run_at` and `last_ok_at`.
- **Default schedules** (overridable per source in YAML):

  | Source kind | Every |
  | --- | --- |
  | Weather alerts | 15 min |
  | Forecast | 3 h |
  | News Flash, calendar | 1 h |
  | Agendas | 2 h |
  | YouTube | 2 h |
  | DBPR | weekly |
  | Sunbiz | daily |

### 5. Source health

- **States:**
  - `ok`
  - `degraded`: the last run failed, or returned zero items while the source usually has some
  - `broken`: 3 consecutive failures, or `healthCheck` failing
- **Tracking:** a `source_runs` table records each run (started, finished, items, new, changed, error) for M8 dashboards and alerts.
- **Display:** a small `pnpm sources:status` CLI prints health per town. The admin UI comes later.

### 6. Data model changes

- `sources`: add `last_run_at`, `consecutive_failures`, `last_error`.
- `records`: add `changed_at`.
- New table `source_runs`.
